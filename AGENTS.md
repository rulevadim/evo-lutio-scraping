# AGENTS.md

## Назначение проекта

Это учебный full-stack пет-проект на Nuxt 4 для чтения блога «Эволюция»
(`evo-lutio.livejournal.com`) в собственном интерфейсе. Приложение скрейпит
последние посты и все их комментарии, сохраняет данные в локальную SQLite,
показывает посты с древовидными комментариями и выполняет полнотекстовый поиск.

Бэкенд не выделен в отдельный сервис: серверные маршруты и вся логика скрейпинга
работают в Nitro под `server/`.

## Стек и команды

- Node.js + TypeScript, Nuxt 4, Vue 3 (`<script setup>`)
- SQLite через `better-sqlite3`; файл данных: `.data/blog.db`
- Tailwind CSS v4 — основной слой вёрстки
- UnoCSS подключён экспериментально, но в текущей разметке не используется
- Пакетный менеджер: `pnpm`

Основные команды:

- `pnpm dev` — локальный сервер на `http://localhost:3000`
- `pnpm dev:debug` — сервер с логированием исходящих HTTP-запросов
- `pnpm build` — сборка и основная проверка типов
- `pnpm preview` — запуск production-сборки
- `pnpm generate` — статическая генерация
- `pnpm test` — Vitest (`*.test.ts` рядом с кодом)

Скрейп-эндпоинты закрыты админ-доступом, поэтому `curl -X POST .../api/scrape`
без сессии вернёт 401. Для локального скрейпинга нужен `.env` (см. `.env.example`):
войти на `/admin` либо передавать куку сессии в curl.

После изменений запускайте `pnpm test` и `pnpm build`; для изменений скрейпера
дополнительно проверяйте соответствующий маршрут вручную, если доступ к
LiveJournal уместен в задаче.

## Структура

- `app/` — клиентская часть Nuxt: страницы, компоненты, composables и CSS
- `server/api/` — Nitro API для постов, комментариев, поиска и запуска скрейпинга
- `server/utils/lj/` — HTTP-клиент и парсинг RSS/JSON-RPC LiveJournal
- `server/db/` — подключение к SQLite, схема (`schema.ts`) и миграция индекса
- `server/middleware/admin-guard.ts` — единственная точка контроля доступа
- `server/utils/pagination.ts` — общие правила пагинации комментариев
- `scripts/` — разовые операции над БД (бэкофилл санитайзера, анализ разметки,
  seed-БД); запускать через `npx tsx`

В Nuxt 4 `srcDir` указывает на `app/`, но `server/` находится в корне проекта.
В серверном коде используйте корневой алиас `~~/server/...`.

## Источник данных и важные инварианты

- Посты берутся из `https://evo-lutio.livejournal.com/data/rss`.
- Полный HTML поста уже находится в RSS `<description>`; страницы отдельных
  постов для получения тела статьи запрашивать не нужно.
- ID поста — `ditemid` из permalink вида `/<ditemid>.html`.
- Комментарии берутся из `__rpc_get_thread` с `expand_all=1`.
- ID комментария — `dtalkid`; `parent_id = 0` означает верхний уровень.
- LiveJournal пагинирует комментарии по 15 верхнеуровневых веток. Вложенные
  ответы приходят вместе со своей веткой.
- Порядок `position` — сквозной threaded pre-order. Не сортируйте комментарии
  заново и не отделяйте ответы от родительской ветки: API пагинации полагается
  на непрерывность этого порядка.
- Скрейпинг идемпотентен: пост обновляется по ID, его старые комментарии и записи
  FTS удаляются и записываются заново в одной транзакции.
- Сохраняйте вежливый режим работы с LiveJournal: единый User-Agent, текущие
  паузы между страницами/постами и разумные предохранители количества запросов.

Не выполняйте реальные запросы к LiveJournal без необходимости при обычной
проверке UI, БД или форматирования. Не добавляйте `.data/blog.db` в git.

## База и поиск

Схема находится в `server/db/schema.ts` (экспортируемой строкой, не в `.sql`-файле:
Nitro бандлит только JS, и чтение файла от `process.cwd()` в проде падало бы с
ENOENT) и применяется при первом `useDb()`. Путь к файлу БД — `DB_PATH` либо
`.data/blog.db`. Таблицы: `posts`, `comments`, виртуальная FTS5-таблица `search`,
key-value `meta` (ключи — в `server/db/meta.ts`).

Поиск использует `unicode61 remove_diacritics 2`: это поиск по словам с
поддержкой кириллицы, но без стемминга. При изменении схемы:

1. сохраняйте совместимость с уже существующей `.data/blog.db` или добавляйте
   явную идемпотентную миграцию;
2. синхронно обновляйте запись данных и FTS-индекс;
3. не меняйте смысл `post_id`, `ref_id`, `position` и `parent_id` без проверки
   поиска, ссылок-якорей и пагинации.

## Правила изменений

- Сохраняйте существующий TypeScript-стиль и форматирование репозитория:
  два пробела, одинарные кавычки, trailing commas, без точек с запятой.
- Для интерфейса используйте Tailwind, если задача явно не посвящена UnoCSS.
- Общую серверную логику держите вне обработчиков API; обработчики должны
  валидировать ввод и делегировать работу утилитам.
- Не дублируйте константы пагинации между клиентом и сервером.
- HTML из LiveJournal хранится как HTML; преобразование в простой текст для FTS
  выполняйте через существующий `htmlToText`.
- Размеры внешних изображений добавляются **на скрейпе** (`savePost`) через
  `reserveImgSpace`; read-эндпоинты отдают HTML как есть. Не переносите сетевой
  probing в браузер из-за CORS.
- Не коммитьте generated/runtime-каталоги: `.nuxt/`, `.output/`, `.data/`,
  `node_modules/`.

## Инварианты безопасности

Проект рассчитан на публичный хостинг. Подробности — в разделе «Безопасность»
`CLAUDE.md`; здесь то, что нельзя нарушать при правках.

- **Весь HTML из ЖЖ проходит `sanitizeLjHtml` перед записью.** Порядок в `savePost`:
  санитизация → `reserveImgSpace` → запись. Не переносите санитизацию внутрь
  `createPersister` (там `db.transaction`) и не пробивайте картинки до неё.
- **При изменении allowlist увеличивайте `HTML_SANITIZER_VERSION`** и прогоняйте
  `scripts/backfill-sanitize.ts` — иначе старый контент останется неочищенным.
  После бэкофилла FTS-индекс пересобирается обязательно.
- **URL, уходящие в `href` мимо HTML-санитайзера** (`authorJournal`, permalink),
  пропускайте через `safeExternalUrl`.
- **Не добавляйте новые write-эндпоинты мимо `isGuarded`** (`server/utils/guarded-routes.ts`)
  и не заменяйте в guard `unsealSession` на `useSession`: последний создаёт сессию
  анониму и падает при пустом пароле.
- **Внешние URL из контента запрашивайте только через `fetchPublic`**, а тело
  читайте через `readCapped`. Голый `fetch` даёт SSRF и неограниченный ответ.
- **Долгие задачи берут `acquireJob`**, а `release()` вызывается в `finally`
  ВНУТРИ stream-задачи, не вокруг возврата стрима.
- На клиенте проверяйте `res.ok` до чтения NDJSON-тела: иначе ошибка разберётся
  как событие и покажется ложный успех.

## Проверка перед завершением

В зависимости от изменения проверьте:

- `pnpm test` и `pnpm build`;
- доступ: аноним не видит кнопок скрейпинга, а POST на них даёт 401;
- список постов и пустое состояние `/`;
- страницу поста, дерево и переключение страниц комментариев;
- поиск по русскому слову, результат поста и переход к комментарию по якорю;
- повторный запуск скрейпинга без дубликатов;
- сохранение целых веток комментариев на одной странице.

Подробное описание текущей архитектуры и HTTP-диагностики также находится в
`CLAUDE.md`; при архитектурных изменениях поддерживайте оба файла согласованными.
